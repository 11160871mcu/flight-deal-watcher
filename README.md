8 條航線未來一年內的直飛來回票價，自動整理成網頁，並在偵測到「真正划算

## 🔍 搜尋策略：雙軌制（Dual-Track）

「未來一年 × 8 條航線 × 5～15 天停留」全部組合起來高達 3 萬多組，不可能
每次都掃過一遍，所以系統設計成兩條軌道同時、交錯進行：

### 1. 近期軌（near track）— 高頻更新
- 範圍：今天起 **90 天內**出發的日期
- 每次執行查 **48 組**（8 條航線平均分配）

### 2. 全年軌（annual track）— 廣度覆蓋
- 範圍：今天起 **12 個月內**出發的日期
- 每次執行查 **96 組**（8 條航線平均分配）

### 3. Cheap Score（便宜指數）—「這個價格算便宜嗎」
- 抓該航線近期（預設 60 天）查到的所有價格組成價格池
- 這次價格贏過價格池裡幾成 → 轉換成 0～100 分
- 是一種**相對排名**：回答「這個價格，在歷史紀錄裡算不算便宜」

### 4. Price Drop 偵測 —「這個價格是不是剛剛才變便宜」
只看**同一組**出發日 / 回程日 / 停留天數，這次查到的價格比**上一次**
查到的價格跌了多少（跟 Cheap Score 是完全不同的訊號，一個看「相對
排名」、一個看「變化量」）。

## 🧭 游標系統（方案 B：固定 epoch，只增不減）

### 舊做法的問題
舊版每次執行都用「今天」當清單的第 0 天，重新產生清單，再靠一個
「位移補償公式」猜游標的新位置。一旦排程漏跑、月份長度不同，或補償
公式算錯，游標就會被侵蝕、原地踏步。

### 新做法：固定起始日（epoch_date），游標永遠只增不減
- `state.json` 新增 `epoch_date`，**只在系統第一次建立時寫入，之後
  永遠不變**，虛擬清單的位置只跟它有關，不會被重新洗牌。
- 游標是**單純累加的整數**：挑到一組或跳過一組（例如出發日已過期），
  都只會 `+1`，不會被扣分、不會因漏跑一輪受罰。

### ⚠️ 為什麼升版後第一次執行，看起來「日期沒有前進」？
這是升版的**必然過渡現象**，不是 bug：

舊版可能已經累積掃到比較遠的日期（例如 10/7），但升版後 `state.json`
的格式改變（version 5 → 6），程式會判定格式不符而**整個重置**：
`epoch_date` 設成「今天」、游標歸零。歸零後，新一輪會從 `epoch_date`
（今天）**照順序重新往前掃**，要花幾天才會「追上」原本已經掃過的位置，
這段期間看起來就像卡住，其實只是在**重複確認已經查過的近期資料**。

**這版已經修正這個過渡痛點**：新增 `bootstrap_cursors_from_history()`，
只在偵測到 state 被升版重置、且 `history.csv` 裡本來就有資料時觸發
**一次**：從既有歷史資料反推「這條航線已經查到最遠的出發日在哪天」，
直接把新游標設到那個位置之後，**不會重新掃過已經查過的近期日期**。

### 怎麼驗證游標真的有在往前走
`latest.json` 新增 `scan_progress` 區塊，記錄：
- `near_laps_completed_avg` / `annual_laps_completed_avg`：近期軌 /
  全年軌平均已經繞了幾圈。**這兩個數字只會增加、不會減少、不會重置**
  （除非你自己改了 `config.yaml` 的搜尋條件觸發新一輪重置）。
- 網頁最下方（篩選面板裡）會直接顯示「📡 掃描進度」，不用自己去看
  JSON，時間久了看這兩個數字持續變大，就代表系統真的有在往前掃。

## 🔔 通知：ntfy.sh 推播（只通知「真正划算」的降價）

### 為什麼要改
原本只要 `price_drop == true`（跟自己上一次比有跌）就會通知，但這樣會
出現「跌了 58%，但本來就貴，跌完還是貴」這種沒意義的通知。

### 新規則：要同時符合兩個條件才通知
1. **`price_drop`**：跟自己上一次查到的價格比，跌幅有達到
   `price_drop_alert_percent`（預設 20%）
2. **`cheap_score >= notify_min_cheap_score`**（預設 `70`，對照網頁
   的分級：90+ 超值／70~89 不錯／40~69 一般／<40 偏貴）：跟同航線
   歷史價格池比，這個價格本身也真的算便宜

兩個都符合，才代表「這是一個剛剛才變便宜、而且現在真的划算」的機票。
